## 二、验收规则分类

### 2.1 编译级别规则（Level 1）

```bash
# RULE-COMPILE-01: 编译通过
mvn clean compile
# 通过条件: 退出码 0，无 ERROR

# RULE-COMPILE-02: 测试编译通过
mvn clean test-compile
# 通过条件: 退出码 0
```

### 2.2 静态分析规则（Level 2）

```bash
# RULE-STYLE-01: Checkstyle 零违规
mvn checkstyle:check
# 通过条件: 零违规

# RULE-BUGS-01: SpotBugs 零告警
mvn spotbugs:check
# 通过条件: 零告警（排除已知排除项）
```

### 2.3 测试级别规则（Level 3）

```bash
# RULE-TEST-01: 所有测试通过
mvn test
# 通过条件: 0 failures, 0 errors

# RULE-TEST-02: 测试覆盖率（Day 22 起生效）
mvn verify -Djacoco.skip=false
# 通过条件: 行覆盖率 >= 20%（初始），逐步提升至 60%
```

### 2.4 架构规范规则（Level 4）

#### RULE-ARCH-01: 包结构合规

**检查内容**：每个模块的包结构是否符合规范

```bash
# 检查 common 层是否包含 starter 包路径
find sloth-boot-common -name "*.java" -exec grep -l "import com.sloth.boot.starter" {} \;
# 通过条件: 无输出

# 检查 starter 之间是否直接依赖
for starter in sloth-boot-starter/*/; do
    name=$(basename "$starter")
    if [ "$name" != "sloth-boot-starter-idempotent" ]; then
        grep -r "sloth-boot-starter-" "$starter/pom.xml" 2>/dev/null | grep -v "sloth-boot-starter-${name##*-}" | grep -v "sloth-boot-starter-redis"
    fi
done
# 通过条件: 无输出（除 idempotent→redis 例外）
```

#### RULE-ARCH-02: 依赖方向合规

```bash
# 检查 common 模块 pom.xml 中是否引用了 starter
grep -r "sloth-boot-starter" sloth-boot-common/*/pom.xml 2>/dev/null
# 通过条件: 无输出

# 检查是否有循环依赖
mvn dependency:tree -pl sloth-boot-common/sloth-boot-common-core | grep "sloth-boot-starter"
# 通过条件: 无输出
```

#### RULE-ARCH-03: 条件装配合规

```bash
# 检查所有 AutoConfiguration 类是否有 @ConditionalOnClass
find sloth-boot-starter -name "*AutoConfiguration.java" -exec grep -L "@ConditionalOnClass" {} \;
# 通过条件: 无输出（所有 AutoConfiguration 类都有 @ConditionalOnClass）

# 检查所有 @Bean 方法是否有 @ConditionalOnMissingBean
find sloth-boot-starter -name "*AutoConfiguration.java" -exec grep -B5 "@Bean" {} \; | \
    grep -A1 "@Bean" | grep -v "@ConditionalOnMissingBean" | grep -v "@Bean" | grep -v "^--$"
# 通过条件: 无输出（或仅包含内部/私有 bean）
```

#### RULE-ARCH-04: package-info 合规

```bash
# 检查每个 Java 包是否都有 package-info.java
find sloth-boot-common sloth-boot-starter -type d -name "java" -prune -o -type d -print | while read dir; do
    if ls "$dir"/*.java >/dev/null 2>&1; then
        if [ ! -f "$dir/package-info.java" ]; then
            echo "MISSING: $dir/package-info.java"
        fi
    fi
done
# 通过条件: 无 MISSING 输出
```

#### RULE-ARCH-05: 配置元数据合规

```bash
# 检查 common-core 中是否包含其他 starter 的配置元数据
python3 -c "
import json
with open('sloth-boot-common/sloth-boot-common-core/src/main/resources/META-INF/spring-configuration-metadata-additional.json') as f:
    data = json.load(f)
    for prop in data.get('properties', []):
        name = prop.get('name', '')
        if name.startswith('sloth.') and not name.startswith('sloth.i18n'):
            print(f'LEAKED: {name}')
"
# 通过条件: 无 LEAKED 输出
```

### 2.5 功能回归规则（Level 5）

```bash
# RULE-FUNC-01: example 工程编译通过
mvn clean compile -pl sloth-boot-example/sloth-boot-example-service

# RULE-FUNC-02: Docker 构建通过（可选）
docker-compose build
```

### 2.6 文档同步规则（Level 6）

```bash
# RULE-DOC-01: README 中的关键类名与代码一致
grep -r "@OperationLog" README.md docs/  # 应为 @OperateLog
# 通过条件: 无输出

# RULE-DOC-02: 配置参考中列出的配置项在代码中存在
# 需要自定义脚本比对 configuration-reference.md 与 @ConfigurationProperties 类

# RULE-DOC-03: 每个 starter 目录下有 README.md
for starter in sloth-boot-starter/*/; do
    if [ ! -f "$starter/README.md" ]; then
        echo "MISSING: ${starter}README.md"
    fi
done
# 通过条件: 无 MISSING 输出（可选，Day 29 完成）
```

## 三、每日验收执行流程

```
1. 执行 Level 1（编译）      → 失败则停止
2. 执行 Level 2（静态分析）   → 失败则标记
3. 执行 Level 3（测试）       → 失败则标记
4. 执行 Level 4（架构规范）   → 失败则标记
5. 执行 Level 5（功能回归）   → 按需执行
6. 执行 Level 6（文档同步）   → 失败则标记
7. 填写验收文档
```

## 四、Claude Code 子代理验收方案

对于无法用纯脚本完成的验收，使用 Claude Code Agent 执行：

### 4.1 命名一致性检查

```
任务: 检查指定模块内所有 Java 类的命名是否符合规范
输入: 模块路径
检查项:
- 类名是否 UpperCamelCase
- 常量是否 UPPER_SNAKE_CASE
- 方法名是否 lowerCamelCase
- 注解名称是否清晰表达意图
输出: 违规列表
```

### 4.2 注释完整性检查

```
任务: 检查指定模块内 public 类和 public 方法的注释完整性
输入: 模块路径
检查项:
- public 类是否有 Javadoc
- public 方法是否有 Javadoc（至少包含功能描述）
- @Deprecated 方法是否有 @see 或 @deprecated 说明
输出: 缺失注释列表
```

### 4.3 日志规范检查

```
任务: 检查指定模块内日志打印是否符合日志规范
输入: 模块路径
检查项:
- 日志消息是否有 [模块标签] 前缀
- 是否使用字符串拼接而非参数化日志
- ERROR 级别是否传递了异常对象
- 是否有明文密码/token 输出
输出: 违规列表
```
