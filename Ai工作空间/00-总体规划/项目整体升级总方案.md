# SlothBoot 项目整体升级总方案

> 文档版本: v1.0 | 制定日期: 2026-05-24 | 制定人: AI 架构升级总负责

## 一、当前问题分析

### 1.1 架构层问题

| 编号 | 问题 | 严重度 | 位置 | 说明 |
|------|------|--------|------|------|
| A-01 | 配置元数据集中污染 | **严重** | `common-core/.../META-INF/additional-spring-configuration-metadata.json` | 992行配置元数据全部写在 common-core 中，包含 20+ 个 starter 的配置项，违反"谁定义谁维护"原则 |
| A-02 | common-core 包含业务逻辑 | **高** | `CacheConstant`, `DataScope`, `DataScopeEnum`, `GenderEnum` | 用户/角色/菜单/部门等缓存前缀、数据权限范围、性别枚举属于业务概念，不应在 common-core |
| A-03 | 请求日志重复记录 | **中** | `common-log/RequestLogFilter` + `starter-web/AccessLogEvent` | 两个 Filter 同时记录 HTTP 请求，字段不同，造成重复和不一致 |
| A-04 | 无结构化日志库 | **中** | 全项目 | JSON 日志通过手动 `JsonUtil.toJson()` 拼接，非标准结构化日志，不利于日志平台解析 |
| A-05 | 日志打印规范缺失 | **中** | 全项目各模块 | 日志消息格式不统一：有的用 `[Tag]` 前缀，有的自由格式；有的手动加 traceId，有的依赖 MDC |
| A-06 | 幂等注解重复定义 | **中** | `starter-redis/IdempotentAspect` + `starter-idempotent/IdempotentAspect` | 两个 starter 都注册幂等切面，通过 `@ConditionalOnMissingBean(type=...)` 字符串回避冲突，方案脆弱 |
| A-07 | OSS/SMS 缺少条件装配 | **中** | `starter-oss/OssAutoConfiguration`, `starter-sms/SmsAutoConfiguration` | 缺少 `@ConditionalOnClass` 守卫，用户配置了 provider 但缺少 SDK 时会报 ClassNotFoundException |
| A-08 | Guava 强制依赖 | **低** | `common-core/pom.xml` | Guava 作为 mandatory 依赖，但 common-core 源码几乎未直接使用，增加传递依赖体积 |
| A-09 | 缺乏模块生命周期管理 | **中** | `starter` 层 | 无统一的 Starter 生命周期顺序管理、健康检查汇总、优雅关闭流程 |
| A-10 | 测试覆盖严重不足 | **高** | 全项目 | 494 个源文件，仅 26 个测试文件，测试比约 5.3% |

### 1.2 规范层问题

| 编号 | 问题 | 说明 |
|------|------|------|
| S-01 | 无统一日志打印规范 | 日志级别使用不一致（info vs debug）、消息格式不统一、敏感数据未脱敏 |
| S-02 | 无统一注释规范 | package-info 存在但不完整，类/方法注释缺失或不规范 |
| S-03 | DTO/VO/Entity 边界模糊 | `common-core/base` 提供了基类，但无使用约束文档 |
| S-04 | 无统一提交规范 | `CONTRIBUTING.md` 有建议但无强制校验 |
| S-05 | 配置属性命名不完全统一 | 大部分使用 `sloth.<module>.*`，但个别模块前缀不一致 |
| S-06 | 无统一异常日志规范 | `GlobalExceptionHandler` 规范较好，但其他模块各自处理异常日志 |

### 1.3 基础设施层问题

| 编号 | 问题 | 说明 |
|------|------|------|
| I-01 | CI 只有编译检查 | GitHub Actions 仅执行 `mvn clean verify`，无代码质量门禁、覆盖率报告、依赖漏洞扫描 |
| I-02 | 无 GraalVM CI | 虽有 `reflect-config.json`，但 CI 不验证 Native Image 编译 |
| I-03 | README 与代码不一致 | README 引用 `@OperationLog`，实际是 `@OperateLog`；配置项名称不匹配 |
| I-04 | CHANGELOG 不完整 | 部分变更未记录 |

## 二、目标架构设计

### 2.1 架构分层（目标）

```
┌─────────────────────────────────────────────────────────────────┐
│                      sloth-boot-example                         │
│                     （示例工程 / 集成验证）                         │
├─────────────────────────────────────────────────────────────────┤
│  starter-web  starter-auth  starter-redis  starter-mybatis      │
│  starter-ai   starter-gateway  starter-feign  starter-mq        │
│  starter-monitor  starter-es  starter-thread-pool  starter-oss  │
│  starter-excel  starter-sentinel  starter-idempotent  starter-sms│
│  starter-job  starter-seata                                     │
│                                                                 │
│                    Starter 层（能力扩展层）                        │
│              高内聚：每个 starter 自包含一种能力                    │
│              低耦合：starter 之间禁止直接依赖                      │
│              统一规范：自动装配、条件加载、元数据自管理               │
├─────────────────────────────────────────────────────────────────┤
│  common-core        common-log         common-security          │
│  common-test        common-doc                                  │
│                                                                 │
│                    Common 层（基础设施层）                         │
│         仅提供：抽象、接口、工具、基类、标准规范                     │
│         禁止：业务逻辑、具体实现、跨模块耦合                        │
├─────────────────────────────────────────────────────────────────┤
│              sloth-boot-dependencies（BOM）                      │
│              sloth-boot-parent（父 POM）                         │
│                    基础 POM 层                                    │
└─────────────────────────────────────────────────────────────────┘
```

### 2.2 核心架构原则

| 原则 | 说明 |
|------|------|
| **单一职责** | 每个模块只做一件事，每个类只承担一个职责 |
| **依赖反转** | common 层定义接口，starter 层提供实现，业务层消费 |
| **配置自治** | 每个 starter 自己管理 `spring-configuration-metadata-additional.json` |
| **事件解耦** | 模块间通过 Spring Event 通信，禁止直接调用其他 starter 的内部类 |
| **条件装配** | 所有 bean 必须有 `@ConditionalOnClass` / `@ConditionalOnMissingBean` |
| **可观测优先** | 每个组件必须有健康检查、MDC 上下文传播、日志输出能力 |
| **规范先行** | 先定规范，再写代码；规范可自动校验 |

### 2.3 包结构规范（目标）

```
com.sloth.boot
  ├── common                        # common 层
  │   ├── core                      # common-core
  │   │   ├── annotation            # 通用注解（非业务）
  │   │   ├── base                  # 基础模型（Entity/DTO/VO/Query）
  │   │   ├── constant              # 通用常量
  │   │   ├── context               # 线程上下文（Trace/User）
  │   │   ├── enums                 # 通用枚举
  │   │   ├── event                 # 事件基础设施
  │   │   ├── exception             # 异常体系
  │   │   ├── result                # 统一响应
  │   │   └── util                  # 工具类
  │   ├── log                       # common-log
  │   │   ├── filter                # Servlet Filter
  │   │   ├── model                 # 日志模型
  │   │   ├── aspect                # AOP 切面
  │   │   ├── event                 # 日志事件
  │   │   └── properties            # 配置属性
  │   ├── security                  # common-security
  │   ├── test                      # common-test
  │   └── doc                       # common-doc
  │
  ├── starter                       # starter 层
  │   ├── web                       # starter-web
  │   │   ├── config                # 自动配置
  │   │   ├── handler               # 处理器
  │   │   ├── filter                # 过滤器
  │   │   ├── properties            # 配置属性
  │   │   └── validator             # 校验器
  │   ├── auth                      # starter-auth（同结构）
  │   └── ...                       # 其他 starter
  │
  ├── generator                     # 代码生成器
```

## 三、模块重构总策略

### 3.1 模块变更清单

#### 保留（不变或微调）

| 模块 | 动作 | 说明 |
|------|------|------|
| `sloth-boot-dependencies` | 保留 | BOM 层，无需变更 |
| `sloth-boot-parent` | 微调 | 移除 Guava 强制依赖，改为按需 optional |
| `sloth-boot-common-test` | 保留 | 测试基础类，后续增强 |
| `sloth-boot-common-doc` | 保留 | Knife4j/OpenAPI 集成，功能独立 |
| `sloth-boot-common-security` | 微调 | 移入 `common-core` 的安全相关工具类（如 `SecurityUtil`），消除重复 |
| `sloth-boot-example` | 重构 | 适配所有规范变更，作为最终集成验证 |

#### 重构

| 模块 | 动作 | 说明 |
|------|------|------|
| **`sloth-boot-common-core`** | **重点重构** | 移除业务逻辑（CacheConstant 业务前缀、DataScope、GenderEnum）；移除集中式元数据 JSON；Guava 改 optional；SecurityUtil 迁移到 common-security |
| **`sloth-boot-common-log`** | **重点重构** | 统一日志体系，消除与 starter-web 的重复日志；引入结构化日志支持；制定日志规范 |
| **`sloth-boot-starter-web`** | **重构** | 移除 `AccessLogEvent`（统一由 common-log 处理）；统一请求/响应日志 |
| **`sloth-boot-starter-redis`** | **重构** | 移除内置 `IdempotentAspect`（幂等能力由 starter-idempotent 独占） |
| **`sloth-boot-starter-monitor`** | **重构** | 移除 `BeanPostProcessor` 强改配置；健康检查标准化 |
| **`sloth-boot-starter-oss`** | **增强** | 增加 `@ConditionalOnClass` 守卫 |
| **`sloth-boot-starter-sms`** | **增强** | 增加 `@ConditionalOnClass` 守卫；修复 TencentSmsClient 构造问题 |
| **`sloth-boot-starter-mybatis`** | **修复** | 添加 `@ConditionalOnClass`；修复 `isDevProfile()` 默认行为 |
| **`sloth-boot-starter-gateway`** | **增强** | 补充 Reactive MDC 支持 |
| **`sloth-boot-generator`** | **增强** | 更新模板以符合新规范 |

#### 新增

| 模块 | 说明 |
|------|------|
| **`sloth-boot-starter-logging`**（可选） | 如果日志能力复杂度超出 common-log 承载，将 HTTP 请求日志、慢操作日志、审计日志的 starter 级能力抽取到此模块 |

#### 删除/合并

| 模块 | 动作 | 说明 |
|------|------|------|
| `CacheConstant` 业务前缀 | **移除** | 保留通用分隔符和前缀模板，业务前缀由各模块自行定义 |
| `DataScope` + `DataScopeEnum` | **迁移到 starter-mybatis** | 属于数据权限实现，不应在 common-core |
| `GenderEnum` | **删除** | 业务枚举，不属于框架层 |
| `starter-redis/IdempotentAspect` | **删除** | 幂等能力由 `starter-idempotent` 独占 |
| `starter-web/AccessLogEvent` 相关逻辑 | **删除** | 请求日志统一由 `common-log` 处理 |

### 3.2 配置元数据治理方案

**当前问题**：`common-core` 中有一个 992 行的 `additional-spring-configuration-metadata.json`，包含了所有 20+ starter 的配置定义。

**目标方案**：
1. 每个 starter 模块在 `src/main/resources/META-INF/` 下维护自己的 `spring-configuration-metadata-additional.json`
2. 从 `common-core` 中完全移除该文件
3. 各 starter 的配置元数据只描述自己的 `sloth.<module>.*` 前缀
4. `common-core` 只保留核心通用配置（如 `sloth.i18n.*`）

## 四、日志体系重构方案

### 4.1 目标架构

```
                    ┌─────────────────────────────────────┐
                    │         统一日志规范层               │
                    │   (日志字段标准、级别标准、格式标准)    │
                    └──────────┬──────────────────────────┘
                               │
              ┌────────────────┼────────────────┐
              │                │                │
     ┌────────▼─────┐  ┌──────▼──────┐  ┌──────▼──────┐
     │  请求日志层   │  │  审计日志层  │  │  业务日志层  │
     │ RequestLog   │  │ OperateLog  │  │  AppLog     │
     └────────┬─────┘  └──────┬──────┘  └──────┬──────┘
              │                │                │
     ┌────────▼────────────────▼────────────────▼──────┐
     │              上下文传播层                         │
     │  TraceContext / UserContext / MDC                │
     │  HTTP → Gateway → Feign → MQ → ThreadPool       │
     └────────────────────┬────────────────────────────┘
                          │
     ┌────────────────────▼────────────────────────────┐
     │              输出层                              │
     │  Console / File / JSON Encoder / ELK / Loki     │
     └─────────────────────────────────────────────────┘
```

### 4.2 日志分类与职责

| 类型 | 职责 | 采集方式 | 存储 | 模块归属 |
|------|------|----------|------|----------|
| **请求日志** | HTTP 请求/响应全记录 | Servlet Filter | 控制台 + 文件 | common-log |
| **审计日志** | 用户操作记录（谁/做了什么/结果） | `@OperateLog` AOP | 事件驱动，由业务持久化 | common-log |
| **慢操作日志** | 慢 SQL、慢 API、慢 ES 查询 | 拦截器/Filter | 事件驱动 + 指标 | 各 starter 发布事件，common-log 提供基类 |
| **错误日志** | 异常统一记录 | `GlobalExceptionHandler` | 控制台 + 文件 | starter-web |
| **业务日志** | 业务流程关键节点 | 手动 `log.info/debug` | 控制台 + 文件 | 业务代码 |

### 4.3 日志字段规范

**通用 MDC 字段（所有日志必须携带）**：

| 字段 | 来源 | 说明 |
|------|------|------|
| `traceId` | TraceFilter 生成 | 全链路追踪 ID |
| `spanId` | TraceContext | 当前跨度 ID |
| `userId` | UserContext | 当前用户 ID |
| `tenantId` | UserContext | 租户 ID |
| `appName` | `spring.application.name` | 应用名 |
| `env` | `spring.profiles.active` | 环境标识 |

**请求日志字段**：method, url, query, clientIp, userAgent, headers(脱敏), body(截断), status, costTime

**审计日志字段**：module, description, operateType, method, requestUrl, requestParams, responseResult, operatorId, operatorName, operatorIp, costTime, status, errorMsg

### 4.4 日志级别规范

| 级别 | 使用场景 | 示例 |
|------|----------|------|
| `ERROR` | 系统异常、不可恢复错误、需要人工介入 | 数据库连接失败、NPE、未捕获异常 |
| `WARN` | 业务异常、可恢复错误、需要关注 | 业务校验失败、远程调用超时后降级 |
| `INFO` | 关键业务流程节点、审计日志、请求日志 | 用户登录、订单创建、接口调用 |
| `DEBUG` | 开发调试信息、方法入参出参 | 方法调用详情、缓存命中/未命中 |
| `TRACE` | 极细粒度调试、框架内部追踪 | SQL 语句参数、消息队列原始消息 |

### 4.5 日志格式规范

**统一格式**：
```
%d{yyyy-MM-dd HH:mm:ss.SSS} [%thread] [%X{traceId:-}] %-5level %logger{36} - %msg%n
```

**日志消息格式**：
```
[模块标签] 关键信息 key1={}, key2={}
```

示例：
```java
// 正确
log.info("[Auth] 用户登录成功 userId={}, ip={}", userId, ip);
log.warn("[Redis] 分布式锁获取超时 lockKey={}, timeout={}ms", key, timeout);
log.error("[MyBatis] 数据库操作异常 sql={}, error={}", sql, e.getMessage(), e);

// 错误（禁止）
log.info("登录成功");  // 无模块标签，无关键参数
log.error("出错了: " + e.getMessage());  // 字符串拼接
```

### 4.6 敏感数据日志脱敏规范

| 数据类型 | 脱敏规则 | 示例 |
|----------|----------|------|
| 手机号 | 保留前3后4 | `138****1234` |
| 身份证 | 保留前4后4 | `1101****1234` |
| 银行卡 | 保留后4 | `****1234` |
| 密码/token | 完全遮蔽 | `******` |
| 邮箱 | 保留首字母和域名 | `z***@example.com` |

## 五、Starter 层增强方案

### 5.1 统一自动装配规范

每个 starter 必须：

1. **类级注解**：
```java
@AutoConfiguration(after = SomeOtherAutoConfiguration.class)
@ConditionalOnClass(RequiredClass.class)
@ConditionalOnProperty(prefix = "sloth.<module>", name = "enabled", havingValue = "true", matchIfMissing = true)
@EnableConfigurationProperties(XxxProperties.class)
public class XxxAutoConfiguration {
```

2. **Bean 级注解**：所有公开 Bean 必须标注 `@ConditionalOnMissingBean`

3. **配置元数据**：每个 starter 自己维护 `spring-configuration-metadata-additional.json`

4. **package-info.java**：每个包必须有

### 5.2 扩展点机制

```
接口/抽象类（common 层定义）
    ↓
默认实现（starter 层提供）
    ↓
@ConditionalOnMissingBean 允许用户覆盖
```

### 5.3 事件总线规范

模块间通信统一使用 Spring ApplicationEvent：

```java
// common-core 提供基类
public class BaseEvent extends ApplicationEvent {
    private String traceId;
    private LocalDateTime eventTime;
}

// starter 发布事件
eventPublisher.publishEvent(new SlowOperationEvent(...));

// 任何模块可监听
@EventListener
public void onSlowOperation(SlowOperationEvent event) { ... }
```

**规则**：
- 事件定义在发布方模块（或 common 层基类中）
- 监听方不依赖发布方的具体类，只依赖事件类
- 异步事件使用 `@Async` + `@EventListener`，由 common-core `EventPublisher` 统一管理

### 5.4 健康检查规范

每个 starter 如果涉及外部依赖，必须提供 `HealthIndicator`：

```java
@Component
@ConditionalOnClass(HealthIndicator.class)
@ConditionalOnBean(ExternalClient.class)
public class XxxHealthIndicator extends AbstractHealthIndicator {
    @Override
    protected void doHealthCheck(Health.Builder builder) {
        // 检查连接、版本、关键指标
    }
}
```

## 六、模块解耦方案

### 6.1 依赖关系规则

```
规则 1: common 层模块之间不允许相互依赖
规则 2: starter 之间不允许直接依赖（sloth-boot-starter-idempotent 依赖 sloth-boot-starter-redis 是唯一例外，需记录决策原因）
规则 3: starter → common-core 是允许的
规则 4: starter → 其他 common 模块是允许的（如 starter-web → common-log）
规则 5: 禁止反向依赖（common → starter）
规则 6: 禁止循环依赖
```

### 6.2 事件解耦清单

| 当前耦合 | 解耦方式 |
|----------|----------|
| starter-web 的 AccessLogEvent | 统一到 common-log 的请求日志 |
| starter-monitor 的慢操作告警 | 各模块发布 `SlowOperationEvent`，monitor 监听 |
| starter-auth 的登录事件 | `LoginEvent` 由 auth 发布，其他模块监听 |
| starter-mq 的消息失败事件 | `MessageFailureLogEvent` 由 mq 发布 |

### 6.3 接口隔离清单

| 接口 | 定义位置 | 实现位置 | 说明 |
|------|----------|----------|------|
| `PermissionService` | starter-auth | 业务层 | 用户权限查询 |
| `OssClient` | starter-oss | starter-oss | 文件存储 |
| `SmsClient` | starter-sms | starter-sms | 短信发送 |
| `DistributedLock` | starter-redis | starter-redis | 分布式锁 |
| `AlarmService` | starter-monitor | starter-monitor | 告警通知 |
| `OperateLogHandler` | common-log | 业务层 | 审计日志持久化 |
| `AiChatClient` | starter-ai | starter-ai | AI 聊天 |

## 七、基础设施补全方案

### 7.1 CI/CD 增强

| 项目 | 当前状态 | 目标状态 |
|------|----------|----------|
| 编译检查 | `mvn clean verify` | 保持 |
| 代码风格 | Checkstyle（编译时） | 保持 + 增加 CI 步骤 |
| 静态分析 | SpotBugs（编译时） | 保持 + 增加 CI 步骤 |

## 十、验收总机制

### 10.1 自动化验收工具链

| 工具 | 用途 | 阶段 |
|------|------|------|
| `mvn clean verify` | 编译 + Checkstyle + SpotBugs + 测试 | 每天 |
| JaCoCo | 测试覆盖率报告 | 阶段五开始 |
| 自定义脚本 | 包结构校验、配置元数据分片校验 | 阶段三四 |
| Claude Code 子代理 | 代码规范审查、命名一致性检查 | 每天 |

### 10.2 验收层级

```
Level 1: 编译通过（mvn clean verify 无错误）
Level 2: 静态分析通过（Checkstyle + SpotBugs 零违规）
Level 3: 测试通过（所有测试绿色）
Level 4: 架构规范通过（包结构、依赖方向、注解使用符合规范）
Level 5: 功能回归通过（example 工程正常运行）
Level 6: 文档同步（配置参考、架构文档与代码一致）
```
