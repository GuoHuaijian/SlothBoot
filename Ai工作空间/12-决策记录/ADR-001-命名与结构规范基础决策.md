## 决策一：Properties 类统一放在 config 包

### 背景
当前 18 个 starter 中，Properties 类的位置不一致：
- 12 个在 `config/` 包（ai, es, feign, gateway, idempotent, job, monitor, mq, mybatis, oss, redis, seata, sentinel, sms, thread）
- 3 个在 `properties/` 包（auth, excel, web）

### 决策
所有 Properties 类统一放在 `config/` 包中。

### 理由
1. `config/` 是多数 starter 的现有做法（12/15），改动最小
2. AutoConfiguration 和 Properties 属于同一"配置层"，放在同一包内高内聚
3. Spring Boot 官方 starter 也倾向于把 Properties 放在 `config` 或与 AutoConfiguration 同包

### 影响
- 需迁移 3 个 starter 的 Properties 类：auth, excel, web
- 需更新对应 import 语句

### 检查方法
```bash
find sloth-boot-starter -name "*Properties.java" -not -path "*/config/*" -not -path "*/test/*"
# 通过条件: 无输出
```

## 决策二：starter 子包使用标准名而非功能细分名

### 背景
当前 starter-redis 有 `bloom/`, `delay/`, `id/`, `limiter/`, `lock/`, `pubsub/` 等细粒度子包。其他 starter 多用 `core/`, `config/`, `handler/` 等标准名。

### 决策
统一使用标准子包名：`config/`, `core/`, `annotation/`, `aspect/`, `filter/`, `handler/`, `interceptor/`, `listener/`, `event/`, `model/`, `spi/`, `health/`, `metrics/`, `endpoint/`, `support/`。

禁止按功能特性创建子包（如 `bloom/`, `delay/`）。相关类应放在 `core/` 或 `support/` 中。

### 理由
1. 统一子包名降低认知成本——新贡献者看到 `core/` 就知道是核心实现
2. 按功能细分会导致包膨胀（redis 有 12 个子包），管理困难
3. 功能边界通过类名和接口体现，不需要额外的包层级

### 影响
- starter-redis 需在重构阶段合并子包（阶段四）
- 新增 starter 必须使用标准子包名

## 决策三：@AutoConfiguration + @ConditionalOnClass 为强制要求

### 背景
当前 starter-mybatis 和 starter-oss 的 AutoConfiguration 缺少 `@ConditionalOnClass`。其他 starter 都有。

### 决策
所有 AutoConfiguration 类**必须**同时具备：
1. `@AutoConfiguration`（禁止 `@Configuration`）
2. `@ConditionalOnClass`（核心依赖类检查）
3. `@ConditionalOnProperty`（模块开关）
4. `@EnableConfigurationProperties`

### 理由
1. 缺少 `@ConditionalOnClass` 会导致 ClassNotFoundException，对用户不友好
2. Spring Boot 官方 starter 全部遵循此规范
3. 用 `@AutoConfiguration` 替代 `@Configuration` 是 Spring Boot 3.x 最佳实践

### 影响
- 需修复 starter-mybatis 和 starter-oss

## 决策四：业务注解迁出 common-core

### 背景
`@DistributedLock`, `@RateLimit`, `@DataScope`, `@InnerAuth`, `@NoRepeatSubmit` 定义在 common-core，但 AOP 实现在各自 starter。

### 决策
注解应与其实现放在同一模块。迁移计划：
- `@DistributedLock` + `@RateLimit` + `@LimitType` → `starter-redis`
- `@Idempotent` + `@IdempotentType` → `starter-idempotent`
- `@DataScope` + `DataScopeEnum` → `starter-mybatis`
- `@InnerAuth` → `starter-auth`
- `@NoRepeatSubmit` → 评估是否被 `@Idempotent` 覆盖，如覆盖则删除
- `@OperateLog` + `OperateTypeEnum` → `common-log`（与日志职责对口）
- `@Desensitize` + `@DesensitizeType` → `common-security`（与安全职责对口）

### 理由
1. common-core 应只包含框架级通用能力，不应包含特定功能的注解
2. 注解与实现在同一模块，降低跨模块耦合
3. 避免 common-core 隐式依赖 starter 的概念模型

### 影响
- 这是**破坏性变更**，所有引用这些注解的 import 路径需要更新
- 需在迁移指南中说明

### 检查方法
```bash
grep -r "import com.sloth.boot.common.annotation.DistributedLock" sloth-boot-common/
grep -r "import com.sloth.boot.common.annotation.RateLimit" sloth-boot-common/
grep -r "import com.sloth.boot.common.annotation.DataScope" sloth-boot-common/
# 通过条件: 无输出（重构后）
```

## 决策五：禁止在 starter 中使用自定义功能子包名

### 背景
starter-redis 使用了 `bloom/`, `delay/`, `id/` 等按功能命名的子包。starter-ai 使用了 `function/`。starter-es 使用了 `document/`, `index/`, `query/` 等。

### 决策
**新增** starter 必须使用标准子包名。**已有** starter 在重构时逐步迁移到标准子包名。

标准子包名：`config`, `core`, `annotation`, `aspect`, `filter`, `handler`, `interceptor`, `listener`, `event`, `model`, `spi`, `health`, `metrics`, `endpoint`, `support`

### 理由
统一包结构降低新贡献者的学习成本。功能边界通过类名区分，不需要包名重复表达。

### 影响
- 已有的 `bloom/`, `delay/`, `id/`, `document/`, `index/`, `query/` 等子包在阶段四重构时合并
- 非破坏性——不影响编译，只影响包路径
