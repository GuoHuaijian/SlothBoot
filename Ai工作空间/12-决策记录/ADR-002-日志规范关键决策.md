## 决策一：日志消息必须以 [模块标签] 开头

### 决策
所有框架级日志（starter 和 common 模块）的消息必须以 `[PascalCase 模块标签]` 开头。

### 理由
1. **可 grep** — `grep "[Redis]" app.log` 即可筛选模块日志
2. **可读性** — 日志行一眼可见来源模块
3. **与现有实践一致** — 当前 starter-ai 已使用 `[AI]`，starter-mq 已使用 `[MQ]`

### 替代方案
- 方案 B：通过 Logger 名称筛选（需记住包名）— 不够直观
- 方案 C：通过 MDC 字段 `module` 筛选 — 需修改 logback 配置，侵入性强

## 决策二：Token/缓存等高频操作使用 DEBUG 而非 INFO

### 决策
Token 创建/消费、缓存命中/未命中、锁获取/释放等高频操作使用 `log.debug`。

### 理由
1. 生产环境默认 INFO 级别，高频操作打 INFO 会产生大量噪音日志
2. 开发环境可临时开 DEBUG 排查问题
3. 当前 `TokenIdempotentService` 使用 `log.info` 记录每次 Token 操作 — 高并发下日志量爆炸

### 影响
- 需修改 `TokenIdempotentService` 的 `log.info` → `log.debug`
- 需审查所有 starter 中类似的高频 info 日志

## 决策三：框架级日志使用英文，业务日志可用中文

### 决策
starter 和 common 模块的日志消息使用英文；业务代码（example、用户业务层）可使用中文。

### 理由
1. 框架面向开源社区，英文日志更通用
2. 日志平台（ELK、Loki）对英文索引更友好
3. 业务层面向特定团队，中文更直观

## 决策四：请求日志和审计日志配置开关独立

### 决策
`LogProperties` 拆分为 `printAccessLog`（控制 RequestLogFilter）和 `printOperateLog`（控制 OperateLogListener）。

### 理由
当前 `printRequestLog` 同时控制两者，用户无法独立开关。场景：
- 需要审计日志但不需要每个 HTTP 请求都记录 → 只开 `printOperateLog`
- 需要请求日志用于调试但不想记录审计 → 只开 `printAccessLog`

### 影响
- `LogProperties` 新增 `printAccessLog` 字段
- `printRequestLog` 标记 `@Deprecated`，保持向后兼容

## 决策五：敏感头遮蔽列表由枚举定义，不硬编码

### 决策
维护一个敏感头名称集合，`RequestLogFilter` 的 `extractHeaders()` 方法遍历该集合进行遮蔽。

当前仅遮蔽 `Authorization`，需扩展为：`Authorization`, `Cookie`, `Set-Cookie`, `X-Forwarded-For`, `Proxy-Authorization`。
